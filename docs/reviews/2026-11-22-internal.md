# Internal security review, 22 Nov 2026

Scope: `contracts/depth-oracle`, `contracts/demo-lender`, `crates/*` (engine, ingest, API,
publisher), `web/`, and the claims in `docs/SECURITY.md`. Method: read every path that handles
external data or a key, check each documented mitigation against the code, try to break the
contracts in tests, run `cargo audit` and `npm audit`. This is a self-review by the authors;
it is not a substitute for the external audit (plan 5.1c).

## Findings

| # | Severity | Area | Finding | Status |
| --- | --- | --- | --- | --- |
| 1 | Medium | ingest | **Pools self-report.** Tokens, reserves and swap quotes come from the pool contract, and Aquarius pools are upgradeable (`apply_upgrade`). An upgraded or malicious pool could report reserves it does not hold and inflate depth. | **Fixed.** Reserves and quoted outputs are checked against `balance(pool)` from the token contracts themselves; a pool reporting more than it holds (0.1% tolerance for accrued fees) is rejected, otherwise the smaller figure is used. All 10 pinned pools pass live. |
| 2 | Medium | docs | **Documented mitigations that did not exist:** a "persistence filter", an "`/offers` reconciliation" test, and a "cross-check against a second endpoint before publishing". | **Fixed in docs.** SECURITY.md and PLAN.md now state what is built. The second-provider cross-check is tracked as plan 5.1b. |
| 3 | Low | oracle | **Unbounded asset list.** The list lives in instance storage, loaded on every call; a compromised publisher could add assets until the instance is too large to load, bricking the oracle. | **Fixed.** `MAX_ASSETS = 200`; new assets beyond it fail with `TooManyAssets`, existing ones still update. Tested. |
| 4 | Low | oracle | **Admin could never change.** A lost or leaked admin key was permanent. | **Fixed.** `set_admin` needs both the current and the new admin's signatures. Tested: one signature is refused, and the old admin loses the role. |
| 5 | Low | deps | `heapless 0.8` (via `stellar-strkey 0.0.16`) carries unsoundness advisories (RUSTSEC-2026-0574/0575/0582 and others). | **Fixed.** Upgraded to `stellar-strkey 1.0.0`; `cargo audit` on the engine is clean. MSRV raised to 1.87. |
| 6 | Info | deps | Contract workspaces report `crypto-bigint` timing (RUSTSEC-2026-0387), `chrono` and `paste` unmaintained. | **Accepted.** All come from the Soroban SDK's test host (`cargo tree -e normal --target wasm32v1-none` shows none in the deployed wasm). Re-check on each SDK upgrade. |
| 7 | Info | web | `postcss` advisory inside Next 15 (build-time processing of our own stylesheet). | **Accepted**, fix needs Next 16; tracked in SECURITY.md. |
| 8 | Info | ingest | Horizon and Soroban RPC are trusted for the data they return. A malicious provider could feed false books or reserves. | **Open** (plan 5.1b): cross-check against a second provider. Mitigated today by on-chain balance checks for pools (finding 1). |
| 9 | Info | publisher | The publisher trusts the local snapshot store: anyone who can write it can make the publisher sign false figures (within the contract's bounds). | **Accepted, documented.** Run the publisher as a separate user with read-only access to the store. |
| 10 | Info | oracle | `samples` in a record is the publisher's claim, not verified on-chain. | **Accepted.** It is informational; readers should rely on `timestamp` and their own `max_age`. |
| 11 | Info | API | No rate limiting; fine on `127.0.0.1`, not for a public bind. | **Documented** in DEPLOY.md: put a reverse proxy with rate limits in front. |
| 12 | Info | demo-lender | Demo only: positions are never reduced, value is supplied by the caller. | **By design**, marked as local-demo code. |

## Found after the review, same day

| # | Severity | Finding | Status |
| --- | --- | --- | --- |
| 13 | Medium | With the new balance checks, the single public RPC rate-limited a live run and six pools were left out; USDY read ~$2K instead of ~$110K. Because the published figure is a 24h minimum, one such run would have depressed it for a day. | **Fixed.** Reads rotate across three providers (each checked to be mainnet), and a run that misses any pinned venue is marked incomplete and excluded from the window. Next live run: 30/30 venues in 6.2 s. |
| 14 | Medium | Sample times were predictable (fixed 30-minute ticks), allowing place-before, cancel-after spoofing. | **Fixed.** Each wait is randomized ±25%. |
| 15 | Low | The $100 floor for helping set the reference was cheap; two small pools at a made-up price could lift the upper median. | **Fixed.** A venue also needs 5% of the deepest venue's depth. Tested. |

## Checked and fine

- Keys: none in the repository or config; the publisher signs through a `stellar` CLI identity
  (macOS Keychain on mainnet); identity names that could be read as flags are rejected; no
  shell is involved (`Command` with an argument list).
- Mainnet: refused without `--mainnet-unaudited`, and never with fewer than 12 samples.
- Oracle: publisher-only writes, strictly increasing timestamps per (asset, band), 60 s future
  skew, 6 h maximum age, value bounds, all-or-nothing batches, TTL extended on publish.
- Reads: simulation only, all-zero source account, network passphrase verified first.
- Identity: SEP-1 checks parse the TOML and require the exact code and issuer pair; SAC ids are
  derived locally and tested against published mainnet ids.
- Arithmetic: checked fixed-point; release builds keep overflow checks on.
- API: GET only, asset codes and bands validated, history capped at 7 days, stale data → 503.
